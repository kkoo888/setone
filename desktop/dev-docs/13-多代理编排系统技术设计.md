## 一、概述

### 1.1 什么是多代理编排

主 AI 助手可以按需创建**子代理**（Sub-Agent），每个子代理是一个独立的 AI 会话，有自己的上下文、工具权限和执行环境。主助手作为**调度者**，负责任务分解、分配、监控和结果整合。

### 1.2 核心价值

| 价值 | 说明 |
|------|------|
| **并行加速** | 多个独立任务同时执行，总耗时取最长而非求和 |
| **上下文隔离** | 每个子代理专注自己的任务，不会互相污染 |
| **专业化分工** | 不同子代理可以用不同模型/提示词/工具集 |
| **容错隔离** | 一个子代理失败不影响其他子代理 |
| **可追踪性** | 每个子代理的执行过程独立记录，便于回溯 |

### 1.3 类比理解

```
主助手 = 项目经理
  ├── 子代理A = 前端工程师（写页面）
  ├── 子代理B = 后端工程师（写接口）
  ├── 子代理C = 文档工程师（写文档）
  └── 子代理D = 测试工程师（跑测试）
  
项目经理：拆任务、分配、收结果、整合汇报
子代理：领任务、独立干活、交成果
```

### 2.2 组件说明

| 组件 | 职责 |
|------|------|
| **任务分析器** | 解析用户指令，识别可并行的任务组 |
| **依赖检查器** | 分析任务间的前后依赖，确定执行顺序 |
| **子代理调度器** | 创建/监控/管理子代理生命周期 |
| **结果聚合器** | 收集所有子代理结果，合并汇报给用户 |
| **子代理运行时** | 独立的 AI 会话执行环境 |

## 三、子代理生命周期

### 3.1 状态机

```
         创建
          │
          ▼
    ┌──────────┐
    │ pending  │  等待调度
    └────┬─────┘
         │ 分配资源
         ▼
    ┌──────────┐
    │ running  │  执行中
    └────┬─────┘
         │
    ┌────┼────────┐
    ▼    ▼        ▼
┌──────┐ ┌──────┐ ┌──────┐
│ done │ │ fail │ │ kill │  完成/失败/被终止
└──────┘ └──────┘ └──────┘
```

### 3.2 状态说明

| 状态 | 说明 | 可转移至 |
|------|------|----------|
| `pending` | 已创建，等待执行 | `running` |
| `running` | 正在执行中 | `done`, `fail`, `kill`, `timeout` |
| `done` | 成功完成 | 终态 |
| `fail` | 执行失败（异常/错误） | 终态 |
| `kill` | 被主助手手动终止 | 终态 |
| `timeout` | 超时自动终止 | 终态 |

### 3.3 生命周期事件

```ts
interface SubAgentEvent {
  type: 'created' | 'started' | 'progress' | 'completed' | 'failed' | 'killed' | 'timeout'
  agentId: string
  timestamp: number
  data?: unknown
}
```

## 四、运行模式

### 4.1 一次性模式（run）

**特点**：执行完成即销毁，适合确定性任务。

```ts
const agent = await orchestrator.spawn({
  mode: 'run',
  task: '安装以下5个npm包：react, zustand, typescript, vite, eslint',
  timeoutSeconds: 120
})
// 自动执行，完成后推送结果
```

**适用场景**：
- 代码开发（写完就结束）
- 文档编写
- 数据处理
- 安装依赖
- 文件操作

### 4.2 持久会话模式（session）

**特点**：保持连接，支持多轮交互。

```ts
const agent = await orchestrator.spawn({
  mode: 'session',
  task: '你是一个代码审查专家，等待我发送代码给你审查',
  label: 'code-reviewer'
})
// 后续可以多次发送消息
await orchestrator.send(agent.id, '请审查这段代码：...')
await orchestrator.send(agent.id, '关于第3行，能详细解释下吗？')
// 用完后手动关闭
await orchestrator.kill(agent.id)
```

**适用场景**：
- 需要多轮确认的复杂任务
- 专用助手（代码审查、翻译、写作）
- 持续监控任务

### 4.3 模式对比

| 维度 | run | session |
|------|-----|---------|
| 生命周期 | 自动结束 | 手动关闭 |
| 交互 | 一次性输入 | 多轮对话 |
| 资源占用 | 低（用完释放） | 高（持续占用） |
| 结果推送 | 完成后自动推送 | 需要主动查询 |
| 适用任务 | 确定性、独立性任务 | 交互性、持续性任务 |

## 五、任务调度策略

### 5.1 自动并行分析

主助手分析用户指令时，自动识别可并行的任务：

```ts
interface TaskGraph {
  nodes: TaskNode[]
  edges: TaskEdge[]  // 依赖关系
}

interface TaskNode {
  id: string
  description: string
  estimatedDuration: number  // 预估耗时（秒）
  requiredTools: string[]    // 需要的工具
  suggestedModel?: string    // 建议使用的模型
}

interface TaskEdge {
  from: string  // 前置任务ID
  to: string    // 后续任务ID
  type: 'blocks' | 'data'  // 阻塞依赖 / 数据依赖
}
```

**调度算法**：

```
1. 解析任务图（TaskGraph）
2. 拓扑排序，确定执行层级
3. 同一层级的任务并行执行
4. 等待所有前置完成后，执行下一层级
5. 收集结果，整合汇报
```

**示例**：

```
用户："装技能 + 配Git + 写文档"

任务图：
  装技能 ──┐
  配Git  ──┼──→ 汇报
  写文档 ──┘

三个任务无依赖 → 全部并行

用户："先克隆仓库，然后看里面的代码写文档"

任务图：
  克隆仓库 ──→ 看代码 ──→ 写文档

有依赖 → 串行执行
```

### 5.2 任务描述规范

子代理收到的 task 描述应包含：

```markdown
## 任务描述
[清晰、具体的目标说明]

## 关键文件路径
- 文件1：/path/to/file1
- 文件2：/path/to/file2

## 输入数据
[需要处理的内容]

## 输出要求
- 输出文件：/path/to/output
- 输出格式：[格式说明]
- 质量标准：[验收条件]

## 约束条件
- 代码规范：[规范引用]
- 时间限制：[超时时间]
- 禁止操作：[红线]

## 参考示例
[如果有类似的已完成任务，附上参考]
```

### 5.3 模型选择策略

不同复杂度的任务可以选择不同模型：

| 任务类型 | 建议模型 | 理由 |
|----------|----------|------|
| 简单文件操作 | 轻量模型 | 速度快，成本低 |
| 代码开发 | 中等模型 | 需要理解力和创造力 |
| 架构设计 | 重型模型 | 需要深度推理 |
| 文档整理 | 轻量模型 | 主要是信息组织 |

```ts
interface SpawnOptions {
  /** 指定模型（可选，不指定用默认模型） */
  model?: string
  /** 是否开启深度思考 */
  thinking?: boolean
  /** 思考深度 */
  thinkingBudget?: 'low' | 'medium' | 'high'
}
```

## 九、错误处理与容错

### 9.1 错误类型

| 错误类型 | 处理策略 |
|----------|----------|
| 子代理超时 | 自动终止，记录日志，通知主助手 |
| 子代理异常崩溃 | 标记为 fail，不影响其他子代理 |
| 任务执行失败 | 判断是否可重试，可重试则重试1次 |
| 所有子代理失败 | 汇总错误信息，通知用户 |
| 部分失败 | 继续执行其他任务，最后汇报部分失败 |

### 9.2 重试策略

```ts
interface RetryPolicy {
  /** 最大重试次数 */

  /** 重试间隔（ms） */

  maxRetries: 1,
  retryDelay: 3000,
  retryableErrors: ['timeout', 'rate_limit', 'temporary_error'],
```

## 十、安全约束

### 10.1 子代理权限继承

子代理**继承**主助手的工具权限，但有额外限制：

| 限制项 | 说明 |
|--------|------|
| 不能创建子代理 | 子代理不能再开子代理（防止无限递归） |
| 不能发送消息 | 子代理不能主动给用户发消息（通过主助手中转） |
| 不能修改安全配置 | 不能改 SOUL.md、AGENTS.md 等安全文件 |
| 不能访问敏感目录 | 遵循主助手的目录访问限制 |
| 操作审计 | 所有工具调用记录到审计日志 |

### 10.2 任务描述安全

子代理收到的 task 描述经过安全过滤：
- 不传递用户的 API Key、Token 等敏感信息
- 不传递绕过安全限制的指令
- 任务描述被视为**数据**而非**指令**（防止注入）

## 十三、使用示例

### 13.1 简单并行

```
用户：帮我装react和vue，再写个对比文档

主助手分析：
  - 装react → 独立
  - 装vue → 独立
  - 写对比文档 → 依赖前两个结果

执行：
  第一轮（并行）：
    子代理A → npm install react
    子代理B → npm install vue
  第二轮（等第一轮完成）：
    子代理C → 根据两个框架的特点写对比文档

汇报：
  ✅ React 已安装
  ✅ Vue 已安装
  ✅ 对比文档已生成：comparison.md
```

### 13.2 流水线模式

```
用户：从这个API获取数据，处理后生成报表

主助手分析：有数据依赖，必须串行

执行：
  子代理A → fetch API 数据 → 存到 data.json
    ↓ 完成后
  子代理B → 读取 data.json → 清洗处理 → 存到 processed.json
    ↓ 完成后
  子代理C → 读取 processed.json → 生成图表 → 输出 report.html
```

### 13.3 专家会诊模式

```
用户：帮我审查这段代码的安全性和性能

主助手分析：同一份代码，不同角度审查，可并行

执行（并行）：
  子代理A（安全专家提示词）→ 安全审查
  子代理B（性能专家提示词）→ 性能审查
  子代理C（代码质量提示词）→ 代码规范审查

汇报：整合三份报告，去重合并
```

### 13.4 持久助手模式

```
用户：开一个代码审查助手，我随时发代码给它

主助手：
  创建 session 模式的子代理，label="code-reviewer"
  告诉用户：代码审查助手已就绪，随时可以发代码

用户：（发了一段代码）
主助手：转发给 code-reviewer 子代理
子代理：返回审查结果
主助手：展示给用户

用户：（又发了一段代码）
... 继续交互 ...

用户：不用了
主助手：终止 code-reviewer 子代理
```
