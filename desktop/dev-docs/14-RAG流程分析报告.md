# RAG 流程分析报告：7 步流水线 vs Smart Desktop Assistant

> 版本：v1.0 | 作者：小希 | 日期：2026-05-20
> 状态：分析完成，待开发

---

## 一、背景

基于 LangChain 的 RAG（检索增强生成）标准 7 步流水线，逐一比对 `smart-desktop-assistant` 项目的 `knowledge-base` 模块实现，识别缺失项和优化空间。

参考文档：LangChain RAG 流程、项目源码 `modules/knowledge-base/`

---

## 二、7 步流程逐步比对

### 第 1 步：🔪 文档加载器（TextExtractor）

| 格式 | 标准做法 | 当前实现 | 状态 |
|------|---------|---------|------|
| PDF | ✅ 必须支持 | ❌ `case '.pdf': return ''` 跳过 | 🔴 **缺失** |
| DOCX | ✅ 必须支持 | ❌ `case '.docx': return ''` 跳过 | 🔴 **缺失** |
| Excel/XLSX | ✅ 企业必备 | ❌ 完全未处理 | 🔴 **缺失** |
| MD/TXT/JSON/CSV | ✅ | ✅ 已支持 | 🟢 完整 |
| YAML/HTML/XML/Parquet | ✅ | ✅ 已支持 | 🟢 完整 |
| ZIP 解压导入 | ⚠️ 加分项 | ✅ 有 ZipExtractor | 🟢 完整 |
| 网页 URL 导入 | ⚠️ 常见需求 | ❌ 未实现 | 🟡 缺失 |
| 数据库连接导入 | ⚠️ 企业需求 | ❌ 未实现 | 🟡 缺失 |

**🔴 关键问题：PDF 和 DOCX 是企业文档的主力格式，不支持等于 RAG 废了一半。**

**建议方案：**
- PDF：集成 `pdf-parse` 或 `pdfjs-dist`（纯 JS，Electron 友好）
- DOCX：集成 `mammoth`（轻量，提取纯文本 + 简单格式）
- XLSX：集成 `xlsx` 库（SheetJS）
- URL：集成 `node-fetch` + HTML 解析提取正文

### 第 2 步：✂️ 文本分割器（SmartChunker / Chunker）

| 功能 | 标准做法 | 当前实现 | 状态 |
|------|---------|---------|------|
| 按段落切分 | ✅ | ✅ `chunkByParagraphs` | 🟢 |
| 按句子边界切分 | ✅ | ✅ `chunkByFixed`（智能边界） | 🟢 |
| 结构化数据切分 | ✅ | ✅ JSON/JSONL/CSV 按记录切 | 🟢 优秀 |
| 保留上下文 overlap | ✅ | ✅ `overlap: 64` | 🟢 |
| 自动检测内容类型 | ✅ | ✅ `detectContentType` | 🟢 |
| 元数据保留 | ✅ 切片应带来源信息 | ⚠️ 只存 chunkIndex，未带标题/章节 | 🟡 可优化 |
| 语义切分 | ⚠️ 按语义边界切 | ❌ 按字数切分 | 🟡 可优化 |

**评价：基础扎实，结构化数据切分是亮点。**

**优化建议：**
- 切片时提取上下文元数据（标题、章节、页码）存入 `kb_chunks` 表的新字段
- 语义切分：利用嵌入向量判断语义边界，段落间向量距离大时切分

---

### 第 3 步：🧠 向量化（EmbeddingService + VectorStore）

| 功能 | 标准做法 | 当前实现 | 状态 |
|------|---------|---------|------|
| 嵌入模型调用 | ✅ | ✅ `nomic-embed-text` via Ollama | 🟢 |
| 批量嵌入 | ✅ | ⚠️ `embedBatch` 串行逐个调用 | 🟡 **需优化** |
| 向量存储 | ✅ | ✅ SQLite BLOB 存储 | 🟢 |
| 余弦相似度 | ✅ | ✅ 手写实现 | 🟢 |
| 索引加速 | ⚠️ HNSW/IVF 等 | ❌ 暴力遍历所有向量 | 🟡 需优化 |
| 增量更新 | ⚠️ 文件变更只更新变化部分 | ❌ 每次全量重新向量化 | 🟡 可优化 |

**🔴 关键问题：`embedBatch` 是串行的，导入大量文档会非常慢。**

**优化建议：**
- `embedBatch` 改为 `Promise.all` 并发，加并发数限制（如 5 个并发）
- 向量索引：文档量 < 10 万时暴力遍历可接受，超过后考虑引入 HNSW
- 增量更新：记录文件 hash，只对变化文件重新向量化

### 第 4 步：🔍 检索器（VectorStore.search）

| 功能 | 标准做法 | 当前实现 | 状态 |
|------|---------|---------|------|
| Top-K 检索 | ✅ | ✅ `search(queryEmbedding, topK)` | 🟢 |
| 相似度阈值过滤 | ✅ 低于阈值不返回 | ❌ 未过滤 | 🟡 缺失 |
| MMR（多样性检索） | ⚠️ 避免返回重复内容 | ❌ 未实现 | 🟡 缺失 |
| 重排序（Reranker） | ⚠️ 二次精排 | ❌ 未实现 | 🟡 缺失 |
| 混合检索 | ⚠️ 向量 + BM25 关键词 | ❌ 只有向量检索 | 🟡 缺失 |
| 多轮对话上下文感知 | ⚠️ 结合对话历史检索 | ❌ 每次独立检索 | 🟡 缺失 |

**评价：基础可用，但检索质量有较大提升空间。**

**优化建议（按优先级）：**
1. **相似度阈值过滤**（低复杂度）：`score < 0.5` 的结果直接丢弃
2. **MMR 多样性**（中复杂度）：避免 Top-K 结果高度相似
3. **混合检索**（中复杂度）：向量检索 + BM25 关键词检索，结果融合
4. **Reranker**（高复杂度）：需要额外的交叉编码器模型

### 第 5 步：📝 Prompt 模板（RAGEngine）

| 功能 | 标准做法 | 当前实现 | 状态 |
|------|---------|---------|------|
| 系统提示词 | ✅ | ✅ `DEFAULT_RAG_SYSTEM_PROMPT` | 🟢 |
| 上下文注入 | ✅ | ✅ `buildContext` 拼接来源 | 🟢 |
| 来源引用 | ✅ | ✅ 带文件名+片段号+相似度 | 🟢 |
| 模板变量 | ⚠️ 可配置模板系统 | ❌ 硬编码在代码里 | 🟡 缺失 |
| Few-shot 示例 | ⚠️ 提供回答示例 | ❌ 未实现 | 🟡 缺失 |
| 角色定制 | ⚠️ 用户可自定义 AI 角色 | ⚠️ 有 SoulManager 但未与 RAG 联动 | 🟡 可优化 |

**优化建议：**
- Prompt 模板存入配置文件，用户可编辑
- Few-shot：在 Prompt 中注入 2-3 个高质量问答示例
- SoulManager 联动：将用户的 SOUL.md 人格设定融入 RAG Prompt

### 第 6 步：🤖 模型调用（OllamaAIService）

| 功能 | 标准做法 | 当前实现 | 状态 |
|------|---------|---------|------|
| 调用 LLM | ✅ | ✅ OllamaAIService | 🟢 |
| 流式输出 | ✅ | ✅ `chatStream` | 🟢 |
| 超时控制 | ✅ | ✅ `fetchWithTimeout` | 🟢 |
| 失败重试 | ⚠️ 网络抖动自动重试 | ❌ 无重试机制 | 🟡 缺失 |
| 多模型路由 | ⚠️ 简单问题用小模型 | ❌ 固定一个模型 | 🟡 缺失 |
| Token 用量追踪 | ⚠️ 监控消耗 | ⚠️ 有 `evalCount` 未持久化 | 🟡 可优化 |

**优化建议：**
- 失败重试：指数退避重试 3 次（1s → 2s → 4s）
- 多模型路由：简单问题用 ministral:3b，复杂问题用 qwen2.5:7b
- Token 追踪：持久化到 SQLite，用于成本分析

### 第 7 步：🍽️ 输出解析

| 功能 | 标准做法 | 当前实现 | 状态 |
|------|---------|---------|------|
| 结构化输出解析 | ✅ JSON/Markdown 格式化 | ❌ 直接返回原始文本 | 🔴 **缺失** |
| 格式验证 | ⚠️ 校验输出是否符合预期 | ❌ 未实现 | 🟡 缺失 |
| 引用标注 | ✅ 标记内容来源 | ⚠️ Prompt 里要求了但未强制解析 | 🟡 可优化 |
| 错误处理 | ✅ | ⚠️ 有 try-catch 无降级策略 | 🟡 可优化 |

**🔴 关键问题：没有 OutputParser，模型返回什么就直接展示，无法保证格式一致。**

**建议方案：**
- 实现轻量 `OutputParser`，支持：
  - `JSONParser`：强制 LLM 返回 JSON，自动修复常见格式错误
  - `MarkdownParser`：提取标题、列表、代码块等结构
  - `CitationParser`：从回答中提取引用来源并高亮
- Prompt 中明确要求输出格式，并给出示例

## 五、LlamaIndex 深度分析与借鉴

### 5.1 LlamaIndex 是什么

LlamaIndex（原 GPT Index）是 **专攻 RAG 的框架**，与 LangChain 的"万能工具箱"定位不同：

| | LangChain | LlamaIndex |
|---|---|---|
| 定位 | 通用 AI 应用框架 | RAG 专家 |
| 范围 | LLM 调用 + Agent + Tool + RAG + Memory | 专注数据索引 + 检索 + 生成 |
| 数据连接器 | 100+ | 150+（LlamaHub） |
| 索引类型 | 仅向量 | 6 种（向量/树/列表/关键词/知识图谱/结构化） |
| 语言 | Python + JS | Python 为主（TS 版存在但生态弱） |

### 5.2 LlamaIndex 6 种索引类型

| 索引类型 | 用途 | 适用场景 |
|---------|------|---------|
| **向量索引** (VectorStoreIndex) | 语义搜索 | "什么是公司战略？" |
| **树索引** (TreeIndex) | 递归总结 | "总结这 10 份报告" |
| **列表索引** (ListIndex) | 综合多数据源 | "对比 A 和 B 产品的数据" |
| **关键词索引** (KeywordTableIndex) | 精确匹配 | "张三的工单" |
| **知识图谱索引** (KnowledgeGraphIndex) | 关系推理 | "谁是张三的上级？" |
| **结构化存储索引** (SQLIndex) | 结构化查询 | "上月销售额多少？" |

**当前项目只有向量索引 1 种，差距明显。**

### 5.3 LlamaIndex 检索后处理（Node Postprocessors）

当前项目完全缺失的环节：

```
检索结果 → 相似度过滤 → 重排序 → 冗余压缩 → 去重融合 → 最终结果
              ↑            ↑          ↑           ↑
           过滤低分     精排相关性   压缩重复内容   合并去重
```

| 后处理器 | 功能 | 收益 |
|---------|------|------|
| SimilarityPostprocessor | 过滤低于阈值的结果 | 避免不相关内容 |
| KeywordNodePostprocessor | 关键词二次过滤 | 精确度提升 |
| SentenceEmbeddingPostprocessor | 句子级重排序 | 相关性排序优化 |
| MetadataReplacementPostprocessor | 元数据替换优化 | 上下文更完整 |
| LongContextReorder | 长上下文重排 | 避免"中间丢失"问题 |

### 5.4 LlamaIndex 响应合成模式

当前项目只有一种模式（拼接上下文 → 生成），LlamaIndex 有 5 种：

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **compact** | 压缩上下文，减少 token 消耗 | 成本敏感场景 |
| **refine** | 多轮迭代，逐步完善答案 | 需要高精度的场景 |
| **tree_summarize** | 递归总结，逐层压缩 | 长文档总结 |
| **accumulate** | 多个子答案合并 | 多数据源综合 |
| **simple_summarize** | 简单截断总结 | 快速回答 |

### 5.5 LlamaIndex 查询引擎高级能力

| 能力 | 说明 | 当前项目 |
|------|------|---------|
| **子问题分解** | 复杂问题拆解为子问题分别检索 | ❌ 无 |
| **多轮 RAG 聊天** | 带对话历史的检索 | ❌ 每次独立检索 |
| **混合检索** | 向量 + 关键词 BM25 融合 | ❌ 仅向量 |
| **递归检索** | 先粗检索再精检索 | ❌ 无 |
| **RAG 评估** | 忠实度/相关性/正确性评分 | ❌ 无 |
| **路由器查询引擎** | 自动选择最佳索引 | ❌ 无 |
