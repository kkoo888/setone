## 一、模块目录结构

```
modules/<module-id>/
├── module.json          # 模块元数据（必须）
├── index.ts             # 模块入口，实现 Module 接口（必须）
├── types.ts             # 类型定义（推荐）
├── services/            # 业务逻辑层（推荐）
│   ├── xxx-service.ts
│   └── ...
├── repositories/        # 数据访问层（推荐，所有 SQL 集中在此）
│   ├── xxx-repository.ts
│   └── ...
├── CHANGELOG.md         # 变更记录（推荐）
└── ui/                  # 前端组件（可选，放在 src/renderer/src/pages/ 下）
    ├── XxxPanel.tsx
    └── ...
```

> **注意**：
> - `ui/` 目录存放的是模块内部的辅助组件。页面级组件应放在 `src/renderer/src/pages/<Name>Page/` 下。
> - `repositories/` 目录存放数据访问层，是唯一允许写 SQL 的地方。Service 层不直接操作 SQL，通过 Repository 访问数据。详见第六节（Repository 数据访问层规范）。

## 二、module.json 规范

```json
{
  "id": "模块唯一ID（小写英文，短横线分隔）",
  "name": "模块中文名称",
  "version": "1.0.0",
  "description": "模块功能描述",
  "author": "作者名",
  "enabled": true,
  "dependencies": ["依赖的模块ID列表"],
  "hostVersion": ">=1.0.0",
  "priority": 10,
  "resourceLimits": { "maxMemoryMB": 128, "maxCpuPercent": 10 },
  "provides": [
    { "type": "tool", "name": "工具名", "description": "工具描述", "priority": 10 }
  ],
  "consumes": [
    { "type": "event", "name": "监听的事件名" }
  ],
  "settings": {
    "自定义配置项": "默认值"
  }
}
```

### 2.1 字段说明

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | ✅ | 模块唯一标识，小写英文 + 短横线 |
| `name` | ✅ | 中文名称，用于 UI 显示 |
| `version` | ✅ | 语义化版本号 |
| `description` | ✅ | 功能描述 |
| `author` | ✅ | 作者名 |
| `enabled` | ✅ | 默认是否启用 |
| `dependencies` | ✅ | 依赖的其他模块 ID（可为空数组 `[]`） |
| `hostVersion` | ✅ | 兼容的宿主版本范围 |
| `priority` | ✅ | 加载优先级，数字越小越先加载 |
| `resourceLimits` | ✅ | 资源限制（内存、CPU） |
| `provides` | ✅ | 模块提供的能力声明（**即使为空也要写 `[]`**） |
| `consumes` | ✅ | 模块消费的事件声明（**即使为空也要写 `[]`**） |
| `settings` | 可选 | 模块自定义配置，运行时可通过 `context.config.settings` 读取 |

### 2.2 settings 配置

`settings` 中定义的配置项会在运行时注入到 `context.config.settings`，模块可以在 `activate()` 中读取：

```json
{
  "settings": {
    "maxHistory": 200,
    "autoBackup": true
  }
}
```

```typescript
async activate(context: ModuleContext): Promise<void> {
  const maxHistory = (context.config.settings?.maxHistory as number) ?? 200
  const autoBackup = (context.config.settings?.autoBackup as boolean) ?? true
}
```

> **注意**：`provides` 和 `consumes` 即使为空也必须写 `[]`，否则 `createScopedEventBus()` 会因 `undefined.filter()` 崩溃。

## 三、index.ts 模板

```typescript
import type { Module, ModuleContext, Capability } from '../../src/main/types/module'
// 导入 Repository 和 Service
import { XxxRepository } from './repositories/xxx-repository'
import { XxxService } from './services/xxx-service'

export default class XxxModule implements Module {
  id = 'xxx'
  meta!: import('../../src/main/types/module').ModuleMeta
  private context!: ModuleContext
  private service!: XxxService

  async activate(context: ModuleContext): Promise<void> {
    this.context = context

    // 1. 创建 Repository（注入 db + logger）
    const repository = new XxxRepository(context.db, context.logger)

    // 2. 创建 Service（注入 Repository + logger）
    this.service = new XxxService(repository, context.logger)

    // 3. 初始化（如需建表或加载缓存）
    await repository.init()

    context.logger.info('XXX模块已激活')
  }

  async deactivate(): Promise<void> {
    // ⚠️ 必须清理所有资源（见第七节）
    this.service = undefined as never
    this.context.logger.info('XXX模块已停用')
  }

  getCapabilities(): Capability[] {
    return [
      {
        type: 'tool',
        name: 'xxx_action',
        description: '执行XXX操作',
        priority: 10,
        moduleId: this.id,  // ⚠️ 必须填写
        parameters: {
          type: 'object',
          properties: {
            target: { type: 'string', description: '操作目标' }
          },
          required: ['target']
        },
        handler: {
          execute: async (p) => {
            const { target } = p as { target: string }
            // 通过 Service 处理业务逻辑，不直接操作 SQL
            return this.service.performAction(target)
          }
        }
      }
    ]
  }
}
```

### 3.1 Module 接口方法

| 方法 | 必须实现 | 说明 |
|------|---------|------|
| `activate(context)` | ✅ | 模块激活时调用，注入上下文 |
| `deactivate()` | ✅ | 模块停用时调用，清理资源 |
| `getCapabilities()` | ✅ | 返回模块提供的所有能力 |
| `getUI()` | 可选 | 返回 React 组件（目前无模块使用，预留接口） |
| `getStatus()` | 可选 | 返回运行状态报告（目前无模块使用，预留接口） |

## 四、ModuleContext 上下文 API ⚠️

`activate(context)` 注入的 `ModuleContext` 包含以下属性：

```typescript
interface ModuleContext {
  eventBus: ScopedEventBus      // 事件总线（见第九节热插拔机制）
  config: ModuleRuntimeConfig   // 运行时配置（见下文）
  ai: AIService                 // AI 服务（调用 LLM）
  llm: { chat(...) }           // LLM 快捷访问
  logger: Logger                // 日志工具
  store: ScopedStore            // 模块私有 KV 存储
  db: DatabaseManager           // SQLite 数据库实例
  getModule(name): Module       // 获取其他已注册模块实例
}
```

### 4.1 常用属性速查

| 属性 | 用途 | 示例 |
|------|------|------|
| `context.logger` | 日志输出 | `context.logger.info('已激活')` |
| `context.db` | SQLite 数据库 | `await context.db.run('CREATE TABLE ...')` |
| `context.ai` | 调用 LLM | `const res = await context.ai.chat(messages)` |
| `context.llm.chat` | LLM 快捷调用 | `const res = await context.llm.chat([{ role: 'user', content: '...' }])` |
| `context.config.dataDir` | 应用数据目录 | `join(context.config.dataDir, 'state.json')` |
| `context.config.settings` | 模块自定义配置 | `context.config.settings?.maxHistory ?? 200` |
| `context.config.get(key)` | 读取全局配置 | `await context.config.get<string>('activeTheme')` |
| `context.config.set(key, val)` | 写入全局配置 | `await context.config.set('activeTheme', id)` |
| `context.config.skillSearchPaths` | 技能搜索路径 | `context.config.skillSearchPaths ?? []` |
| `context.eventBus` | 事件总线 | `context.eventBus.on('xxx', handler)` |
| `context.getModule()` | 跨模块调用 | `const skill = context.getModule('skill')` |

## 五、ESM 模块规范 ⚠️

**项目使用 ESM 模块系统（`"type": "module"`），CommonJS 语法全部失效！**

### 5.1 禁止使用 require

```typescript
// ❌ 错误 — 运行时直接报错 ReferenceError: require is not defined
const { BrowserWindow } = require('electron')
const path = require('path')

// ✅ 正确 — 使用 import
import { BrowserWindow } from 'electron'
import { join } from 'path'
```

### 5.2 禁止使用 __dirname / __filename

```typescript
// ❌ 错误 — 运行时直接报错 ReferenceError: __dirname is not defined
const preloadPath = join(__dirname, 'preload.js')

// ✅ 正确 — 手动计算
import { join, dirname } from 'path'
import { fileURLToPath } from 'url'

const __dirname = dirname(fileURLToPath(import.meta.url))
const preloadPath = join(__dirname, 'preload.js')
```

### 5.3 ESM 标准导入写法速查

| 场景 | CommonJS（❌ 禁止） | ESM（✅ 正确） |
|------|---------------------|---------------|
| 默认导入 | `const x = require('x')` | `import x from 'x'` |
| 命名导入 | `const { a, b } = require('x')` | `import { a, b } from 'x'` |
| 当前目录 | `__dirname` | `dirname(fileURLToPath(import.meta.url))` |
| 当前文件 | `__filename` | `fileURLToPath(import.meta.url)` |
| 动态导入 | `require(变量)` | `await import(变量)` |
| JSON 导入 | `require('./x.json')` | `import x from './x.json' with { type: 'json' }` |

### 5.4 原生模块的 createRequire 模式

C++ 原生模块（如 `robotjs`）不支持 ESM `import`，需要使用 `createRequire`：

```typescript
import { createRequire } from 'module'
import { fileURLToPath } from 'url'

const _require = createRequire(fileURLToPath(import.meta.url))

// 原生 C++ 模块只能用 require 加载
const robotjs = _require('robotjs')
```

> **适用场景**：仅限不支持 ESM 的原生 C++ addon。普通 npm 包一律用 `import`。

### 5.5 常见 ESM 报错对照表

| 报错信息 | 原因 | 修复 |
|---------|------|------|
| `require is not defined` | 使用了 CommonJS 的 require | 改用 import |
| `__dirname is not defined` | 使用了 CJS 的 __dirname | 用 import.meta.url 计算 |
| `__filename is not defined` | 使用了 CJS 的 __filename | 用 import.meta.url 计算 |
| `module is not defined` | 使用了 CJS 的 module.exports | 改用 export |
| `exports is not defined` | 使用了 CJS 的 exports | 改用 export |
| `SyntaxError: Unexpected identifier 'assert'` | JSON 导入用了旧语法 | 改为 `with { type: 'json' }` |

### 5.6 模块编译与加载机制

#### 开发环境

- 模块目录：`modules/`
- 文件格式：`.ts` 源码
- 加载方式：`module-loader.ts` 直接 `await import()` 加载 `.ts` 文件
- import 路径：**不需要手动加 `.js` 扩展名**

```typescript
// 开发时这样写即可（不加 .js）
import { CalendarStore } from './services/calendar-store'
import type { CalEvent } from './types'
```

#### 生产环境

- 模块目录：`modules-dist/`（编译产物）
- 文件格式：`.js`（esbuild 编译）
- 编译命令：`npm run build:modules`（或 `npm run build`，会自动先执行 `prebuild`）
- import 路径：编译脚本自动补 `.js` 扩展名

#### 编译流程

```
npm run build
  → prebuild: node scripts/clean.js && node scripts/build-modules.mjs
    → build-modules.mjs:
      1. 遍历 modules/ 下所有 .ts 文件
      2. esbuild 逐文件编译为 .js（format=esm, target=es2022）
      3. 复制 module.json 到 modules-dist/
      4. fixEsmImportExtensions() 自动给相对 import 补 .js 扩展名
  → build: electron-vite build（编译 main/preload/renderer）
```

> **开发者只需写 `.ts` import 不加 `.js`**，编译脚本会自动处理扩展名。

## 六、Repository 数据访问层规范 ⚠️

**所有涉及数据库操作的模块，必须将 SQL 集中在 Repository 层，Service 层禁止直接写 SQL！**

### 6.1 分层架构

```
┌─────────────────────────────────────────────────┐
│              Module (index.ts)                   │  ← 对外暴露 Capability
├─────────────────────────────────────────────────┤
│              Service Layer                       │  ← 业务逻辑编排
│         XxxService / XxxManager                  │     组合多个 Repository
├─────────────────────────────────────────────────┤
│            Repository Layer                      │  ← 数据访问（唯一接触 SQL 的层）
│         XxxRepository                            │     每张表对应一个 Repository
├─────────────────────────────────────────────────┤
│           DatabaseManager                        │  ← 基础设施（better-sqlite3 封装）
└─────────────────────────────────────────────────┘
```

**依赖规则（基于 P3C 应用分层规约）：**
- Service 可以依赖多个 Repository
- Repository **不能**依赖 Service
- Repository **不能**依赖其他 Repository（除非通过 Service 编排）
- Module（index.ts）**不能**直接写 SQL，必须通过 Repository

### 6.2 目录与命名

```
modules/<module-id>/
├── repositories/                # 数据访问层目录
│   ├── xxx-repository.ts        # 单表 CRUD
│   └── yyy-repository.ts        # 另一张表
├── services/
│   └── xxx-service.ts           # 业务逻辑
└── index.ts
```

| 元素 | 命名规范 | 示例 |
|------|---------|------|
| 目录名 | `repositories`（复数） | 与 `services` 对齐 |
| 文件名 | `kebab-case` + `-repository` | `calendar-event-repository.ts` |
| 类名 | `PascalCase` + `Repository` | `CalendarEventRepository` |

### 6.3 方法命名规约（P3C Service/DAO 方法命名）

| 操作 | 方法前缀 | 返回值 | 示例 |
|------|---------|--------|------|
| 获取单个 | `findById` | `Promise<T \| undefined>` | `findById(id)` |
| 获取多个 | `findAll` / `findBy*` | `Promise<T[]>` | `findByDocumentId(docId)` |
| 统计 | `count` / `countBy*` | `Promise<number>` | `countByStatus('active')` |
| 插入/更新 | `save` | `Promise<void>` | `save(entity)` |
| 删除 | `removeById` / `removeBy*` | `Promise<boolean>` | `removeById(id)` |
| 存在判断 | `existsById` | `Promise<boolean>` | `existsById(id)` |
| 分页查询 | `findPage` | `Promise<PageResult<T>>` | `findPage(query)` |

**命名约束：**
- ✅ `findById`、`findByDocumentId`、`findAll`
- ❌ `getById`、`loadAll`、`fetch`、`query`（不使用这些前缀）
- 统一用 `find` 前缀表示查询，`save` 表示持久化，`remove` 表示删除

### 6.4 查询参数封装（P3C Query 对象）

超过 2 个查询参数时，**禁止使用散装参数**，必须封装为 Query 对象：

```typescript
// ❌ 反例 — 参数过多
async findByConditions(
  status: string, startDate: number, endDate: number,
  keyword: string, limit: number, offset: number
): Promise<Event[]> { ... }

// ✅ 正例 — Query 对象封装
interface EventQuery {
  status?: string
  startDate?: number
  endDate?: number
  keyword?: string
  limit?: number
  offset?: number
}

async findByQuery(query: EventQuery): Promise<Event[]> { ... }
```

### 6.5 Repository 实现模板

```typescript
import type { DatabaseManager } from '../../../src/main/types/database'
import type { Logger } from '../../../src/main/types/logger'

/** 数据库行映射接口 — 对应表结构（snake_case） */
interface CalendarEventRow {
  id: string
  title: string
  description: string
  start_time: number
  end_time: number
  color: string
  all_day: number
  reminder: number
}

/** 领域实体 — 对应业务对象（camelCase） */
export interface CalendarEvent {
  id: string
  title: string
  description: string
  startTime: number
  endTime: number
  color: string
  allDay: boolean
  reminder: number
}

/**
 * 日历事件 Repository
 * 负责 calendar_events 表的 CRUD 操作
 * 所有 SQL 集中在此，Service 层不接触 SQL
 *
 * @author 小茜
 * @date 2026-05-20
 */
export class CalendarEventRepository {
  constructor(
    private readonly db: DatabaseManager,
    private readonly logger: Logger
  ) {}

  /**
   * 初始化数据库表
   * 在模块 activate() 中调用
   */
  async init(): Promise<void> {
    await this.db.run(`
      CREATE TABLE IF NOT EXISTS calendar_events (
        id TEXT PRIMARY KEY,
        title TEXT NOT NULL,
        description TEXT NOT NULL DEFAULT '',
        start_time INTEGER NOT NULL,
        end_time INTEGER NOT NULL,
        color TEXT NOT NULL DEFAULT '#4A90D9',
        all_day INTEGER NOT NULL DEFAULT 0,
        reminder INTEGER NOT NULL DEFAULT 15
      )
    `)
  }

  /**
   * 根据 ID 查询事件
   *
   * @param id - 事件 ID
   * @returns 事件实体，不存在时返回 undefined
   */
  async findById(id: string): Promise<CalendarEvent | undefined> {
    const row = await this.db.get<CalendarEventRow>(
      'SELECT * FROM calendar_events WHERE id = ?',
      [id]
    )
    return row ? this.toEntity(row) : undefined
  }

  /**
   * 查询所有事件（按开始时间升序）
   */
  async findAll(): Promise<CalendarEvent[]> {
    const rows = await this.db.query<CalendarEventRow>(
      'SELECT * FROM calendar_events ORDER BY start_time ASC'
    )
    return rows.map(row => this.toEntity(row))
  }

  /**
   * 按时间范围查询事件
   */
  async findByDateRange(startDate: number, endDate: number): Promise<CalendarEvent[]> {
    const rows = await this.db.query<CalendarEventRow>(
      'SELECT * FROM calendar_events WHERE start_time >= ? AND end_time <= ? ORDER BY start_time ASC',
      [startDate, endDate]
    )
    return rows.map(row => this.toEntity(row))
  }

  /**
   * 保存事件（新增或更新，INSERT OR REPLACE）
   */
  async save(event: CalendarEvent): Promise<void> {
    await this.db.run(
      `INSERT OR REPLACE INTO calendar_events
       (id, title, description, start_time, end_time, color, all_day, reminder)
       VALUES (?, ?, ?, ?, ?, ?, ?, ?)`,
      [event.id, event.title, event.description, event.startTime, event.endTime,
       event.color, event.allDay ? 1 : 0, event.reminder]
    )
  }

  /**
   * 批量保存事件（事务内执行）
   */
  async saveAll(events: CalendarEvent[]): Promise<void> {
    await this.db.transaction(async () => {
      for (const event of events) {
        await this.save(event)
      }
    })
  }

  /**
   * 根据 ID 删除事件
   */
  async removeById(id: string): Promise<boolean> {
    const result = await this.db.run(
      'DELETE FROM calendar_events WHERE id = ?',
      [id]
    )
    return result.changes > 0
  }

  /**
   * 统计事件总数
   */
  async count(): Promise<number> {
    const row = await this.db.get<{ cnt: number }>(
      'SELECT COUNT(*) AS cnt FROM calendar_events'
    )
    return row?.cnt ?? 0
  }

  /**
   * 判断事件是否存在
   */
  async existsById(id: string): Promise<boolean> {
    const row = await this.db.get<{ cnt: number }>(
      'SELECT COUNT(*) AS cnt FROM calendar_events WHERE id = ?',
      [id]
    )
    return (row?.cnt ?? 0) > 0
  }

  // ─── 行映射（私有方法，类内放在最后） ──────────────

  /**
   * 数据库行 → 领域实体
   * 处理 snake_case → camelCase 转换及类型映射
   */
  private toEntity(row: CalendarEventRow): CalendarEvent {
    return {
      id: row.id,
      title: row.title,
      description: row.description,
      startTime: row.start_time,
      endTime: row.end_time,
      color: row.color,
      allDay: row.all_day === 1,
      reminder: row.reminder
    }
  }
}
```

### 6.6 带内存缓存的 Repository

对于高频读取场景，可在 Repository 内部维护缓存，但**缓存逻辑必须对 Service 透明**：

```typescript
/**
 * 剪贴板 Repository（带内存缓存）
 *
 * 特点：
 * - 启动时全量加载到内存
 * - 写操作同步更新缓存 + 异步持久化
 * - 缓存对 Service 层透明
 */
export class ClipboardRepository {
  private cache: ClipItem[] = []
  private loaded = false

  constructor(
    private readonly db: DatabaseManager,
    private readonly logger: Logger,
    private readonly maxCacheSize: number = 500
  ) {}

  /** 初始化缓存（模块 activate 时调用） */
  async init(): Promise<void> {
    await this.ensureTable()
    const rows = await this.db.query<ClipItemRow>(
      'SELECT * FROM clipboard_history ORDER BY created_at DESC LIMIT ?',
      [this.maxCacheSize]
    )
    this.cache = rows.map(row => this.toEntity(row))
    this.loaded = true
    this.logger.info(`剪贴板缓存已加载：${this.cache.length} 条`)
  }

  /** 获取缓存（同步，高频调用） */
  getCache(): ClipItem[] {
    return [...this.cache]
  }

  async findById(id: string): Promise<ClipItem | undefined> {
    return this.cache.find(c => c.id === id)
  }

  async save(item: ClipItem): Promise<void> {
    const idx = this.cache.findIndex(c => c.id === item.id)
    if (idx >= 0) {
      this.cache[idx] = item
    } else {
      this.cache.unshift(item)
      if (this.cache.length > this.maxCacheSize) {
        this.cache = this.cache.slice(0, this.maxCacheSize)
      }
    }
    await this.db.run(
      'INSERT OR REPLACE INTO clipboard_history (id, content, type, created_at, pinned) VALUES (?, ?, ?, ?, ?)',
      [item.id, item.content, item.type, item.createdAt, item.pinned ? 1 : 0]
    )
  }

  async removeById(id: string): Promise<boolean> {
    const idx = this.cache.findIndex(c => c.id === id)
    if (idx >= 0) this.cache.splice(idx, 1)
    const result = await this.db.run('DELETE FROM clipboard_history WHERE id = ?', [id])
    return result.changes > 0
  }

  // ... 其他方法 + toEntity() 私有方法
}
```

```typescript
 * 日历事件 Service
 * 负责业务逻辑编排，不直接操作 SQL

export class CalendarEventService {
  constructor(
    private readonly repository: CalendarEventRepository,
    private readonly logger: Logger
  ) {}

  /**
   * 创建事件（含业务校验）
   */
  async createEvent(params: CreateEventParams): Promise<CalendarEvent> {

      throw new AppError(ErrorCode.VALIDATION_ERROR, '事件标题不能为空')
    }

      id: randomUUID(),
      title: params.title.trim(),
      description: params.description ?? '',
      startTime: params.startTime,
      endTime: params.endTime,
      color: params.color ?? '#4A90D9',
      allDay: params.allDay ?? false,
      reminder: params.reminder ?? 15
    }

    // 3. 持久化（通过 Repository）
    await this.repository.save(event)
    this.logger.info(`事件已创建：${event.title}`)
    return event
  }

   * 获取今日事件

  }
```

### 6.11 事务规范

- **事务由 Service 层发起**，Repository 层不管理事务（单表批量除外）
- 涉及多表操作时，Service 调用 `db.transaction()` 包裹多个 Repository 调用
- 单表批量操作在 Repository 内部使用事务

```typescript
// ✅ Service 管理多表事务
async importDocument(file: FileData): Promise<void> {
  await this.db.transaction(async () => {
    await this.docRepository.save(document)
    await this.chunkRepository.saveAll(chunks)
    await this.docRepository.updateChunkCount(document.id, chunks.length)
  })
}

// ✅ Repository 单表批量事务
async saveAll(events: CalendarEvent[]): Promise<void> {
  await this.db.transaction(async () => {
    for (const event of events) {
      await this.save(event)
    }
  })
}
```

## 八、deactivate() 资源清理规范 ⚠️

**这是最容易遗漏的部分！** 每个模块停用时必须清理所有资源，否则会造成内存泄露和功能异常。

### 8.1 必须清理的资源类型

| 资源类型 | 清理方式 | 示例 |
|---------|---------|------|
| **eventBus 监听** | `context.eventBus.off(event, handler)` | 取消所有 `.on()` 注册 |
| **定时器** | `clearTimeout(timer)` / `clearInterval(id)` | 清理所有 setTimeout/setInterval |
| **数据库引用** | `this.db = undefined as never` | 断开 DB 引用 |
| **文件监听** | `watcher.unwatchAll()` | 停止所有文件监听 |
| **外部进程** | `process.kill()` / `child.kill()` | 终止子进程 |
| **Electron 资源** | `tray.destroy()` / `globalShortcut.unregisterAll()` | 清理原生资源 |

### 8.2 eventBus 监听清理模板

```typescript
export default class XxxModule implements Module {
  private context!: ModuleContext
  private eventHandler?: (data: unknown) => void  // ⚠️ 保存引用

  async activate(context: ModuleContext): Promise<void> {
    this.context = context
    
    // ⚠️ 保存 handler 引用，以便 deactivate 时取消
    this.eventHandler = (data: unknown) => {
      // 处理逻辑
    }
    context.eventBus.on('some:event', this.eventHandler)
  }

  async deactivate(): Promise<void> {
    // ⚠️ 取消 eventBus 监听
    if (this.eventHandler) {
      this.context.eventBus.off('some:event', this.eventHandler)
      this.eventHandler = undefined
    }
    this.context.logger.info('XXX模块已停用')
  }
}
```

### 8.3 定时器清理模板

```typescript
export default class XxxModule implements Module {
  private timers = new Map<string, NodeJS.Timeout>()

  async deactivate(): Promise<void> {
    // ⚠️ 清理所有定时器
    for (const timer of this.timers.values()) {
      clearTimeout(timer)
    }
    this.timers.clear()
  }
}
```

### 8.4 完整 deactivate 检查清单

在编写 `deactivate()` 时，逐项检查：

- [ ] 所有 `eventBus.on()` 是否有对应的 `eventBus.off()`？
- [ ] 所有 `setTimeout` / `setInterval` 是否已 `clearTimeout` / `clearInterval`？
- [ ] 所有 `db` 引用是否已清理？
- [ ] 所有文件监听是否已停止？
- [ ] 所有外部进程是否已终止？
- [ ] 所有 Electron 原生资源是否已销毁？

## 九、热插拔机制

### 9.1 模块生命周期

```
discovered → loading → active ⇄ disabled
                          ↓
                        error → (retry / disabled)
```

### 9.2 禁用模块的完整链路

用户在 ModulesPage 点击关闭开关时：

```
前端 toggleModule(id)
  → 调用 IPC 'module:disable'
  → moduleManager.disableModule(id)
  → config 保存禁用状态
  → loader.deactivate(id)
  → 模块实例.deactivate()  ← 你的清理代码在这里
  → reg.instance = null
  → eventBus.emit('on_module_unloaded', { moduleId })
  → unregisterModuleCapabilities(moduleId)  ← 自动注销 IPC
  → 前端侧边栏隐藏入口  ← Sidebar 自动响应
  → 如果当前在该模块页面，自动跳转到对话页
```

### 9.3 启用模块的完整链路

```
前端 toggleModule(id)
  → 调用 IPC 'module:enable'
  → moduleManager.enableModule(id)
  → config 移除禁用状态
  → loader.activate(id)
  → 模块实例.activate(context)
  → eventBus.emit('on_module_unloaded', { moduleId })  ← 注销旧 IPC
  → registerModuleCapabilities()  ← 重新注册 IPC
  → 前端侧边栏显示入口
```

### 9.4 事件消费实现

`module.json` 中的 `consumes` 是声明性元数据，不会自动触发事件监听。模块需要在 `activate()` 中手动订阅：

```typescript
async activate(context: ModuleContext): Promise<void> {
  this.context = context

  // 监听其他模块发出的事件
  this.fileChangeHandler = (data) => { /* 处理 */ }
  context.eventBus.on('file:changed', this.fileChangeHandler)

  // 监听框架事件
  this.moduleLoadHandler = (data) => { /* 处理 */ }
  context.eventBus.on('on_module_loaded', this.moduleLoadHandler)
}

async deactivate(): Promise<void> {
  // ⚠️ 必须取消监听
  if (this.fileChangeHandler) {
    this.context.eventBus.off('file:changed', this.fileChangeHandler)
  }
  if (this.moduleLoadHandler) {
    this.context.eventBus.off('on_module_loaded', this.moduleLoadHandler)
  }
}
```

常用框架事件：

| 事件名 | 触发时机 | 数据 |
|--------|---------|------|
| `on_module_loaded` | 模块激活完成 | `{ moduleId: string }` |
| `on_module_unloaded` | 模块停用完成 | `{ moduleId: string }` |
| `file:changed` | 文件变更（file 模块） | `{ path, event }` |
| `notify` | 发送通知 | `{ title, body, level }` |
| `cron:fired` | 定时任务触发 | `{ jobId }` |

## 十、常见错误与解决

### 9.1 `No handler registered for 'xxx'`

**原因**：模块的工具没有注册为 IPC 处理器  
**解决**：确保 `module.json` 的 `provides` 中声明了该工具，且 `getCapabilities()` 返回了对应的 handler

### 9.2 禁用模块后功能仍然可用

**原因**：deactivate 未清理资源，或 IPC 处理器未注销  
**解决**：按第八节规范编写 deactivate()

### 9.3 重新启用模块后功能异常

**原因**：上次 deactivate 清理不彻底，残留了旧状态  
**解决**：activate 中重新初始化所有资源，不要依赖上次的实例状态

### 9.4 `undefined\SKILL.md` 路径错误

**原因**：`skill_list` 返回数据缺少 `path` 字段  
**解决**：确保 `getCapabilities()` 返回的数据包含所有前端需要的字段

### 9.5 `Cannot read properties of undefined (reading 'filter')`

**原因**：`module.json` 中没有声明 `provides` 或 `consumes` 字段  
**解决**：即使没有能力/事件，也要写空数组 `"provides": [], "consumes": []`

## 十一、工具参数 Schema 规范 ⚠️

**这是让 LLM 正确调用工具的关键！** 如果工具没有参数定义，LLM 不知道该传什么参数，会乱传或直接不调用。

### 10.1 问题背景

`ipc-handlers/ai.handlers.ts` 中的 `collectModuleTools()` 会将模块工具注册给 LLM 使用。参数来源有三级回退：

```
模块自定义参数(cap.parameters) → 静态映射表(TOOL_PARAM_SCHEMAS) → 空 schema
```

如果三级都为空，LLM 看到的工具参数是 `{ properties: {} }`，完全不知道需要什么参数。

### 10.2 新增模块必须做

在 `getCapabilities()` 返回的每个 tool 类型能力中，**必须**通过以下方式之一提供参数定义：

#### 方式一：在 Capability 中直接定义（推荐）

```typescript
getCapabilities(): Capability[] {
  return [
    {
      type: 'tool',
      name: 'xxx_action',
      description: '执行XXX操作',
      priority: 10,
      moduleId: this.id,
      // ✅ 直接定义参数 schema
      parameters: {
        type: 'object',
        properties: {
          target: { type: 'string', description: '操作目标' },
          count: { type: 'number', description: '数量', default: 1 }
        },
        required: ['target']
      },
      handler: {
        execute: async (p) => {
          const { target, count } = p as { target: string; count?: number }
          // ...
        }
      }
    }
  ]
}
```

#### 方式二：在 tool-param-schemas.ts 中添加映射

如果不想在模块代码中写 schema，可以在 `src/main/core/tool-param-schemas.ts` 的 `TOOL_PARAM_SCHEMAS` 对象中添加：

```typescript
xxx_action: {
  type: 'object',
  properties: {
    target: { type: 'string', description: '操作目标' },
    count: { type: 'number', description: '数量', default: 1 }
  },
  required: ['target']
},
```

### 10.3 参数 Schema 编写规范

| 字段 | 说明 | 示例 |
|------|------|------|
| `type` | 参数类型 | `'string'` / `'number'` / `'boolean'` / `'array'` / `'object'` |
| `description` | 参数用途描述（LLM 靠这个理解参数含义） | `'要读取的文件路径'` |
| `required` | 必填参数列表 | `['path', 'content']` |
| `enum` | 可选值枚举 | `['left', 'right', 'middle']` |
| `default` | 默认值 | `1` / `'left'` |
| `items` | 数组元素类型（type=array 时） | `{ type: 'string' }` |

### 10.4 Handler 返回格式规范

handler 的 `execute()` 必须返回 `CapabilityResult`：

```typescript
// ✅ 成功
return { success: true, data: results }

// ✅ 成功（带消息）
return { success: true, data: null, message: '操作完成' }

// ✅ 业务失败（预期的错误）
return { success: false, error: '日程不存在' }

// ❌ 不要直接 throw（除非是意外异常）
throw new Error('日程不存在')  // 这会导致框架捕获并记录错误日志
```

**规则**：
- 预期的业务错误 → 返回 `{ success: false, error: '...' }`
- 意外的系统错误 → 可以 throw，框架会捕获

### 10.5 检查清单

新增或修改模块工具后，逐项检查：

- [ ] 每个 tool 类型能力都有参数定义（方式一或方式二）

- [ ] 必填参数列在 `required` 中
- [ ] 有可选值的参数加了 `enum`
- [ ] 参数名与 handler 中解构的变量名一致

## 十五、前后端对齐规范（踩坑记录）⚠️

**以下问题曾导致多个模块"有界面但功能不生效"，务必避免！**

### 14.1 类型文件必须存在

前端页面如果 import 了类型文件，该文件**必须存在**，否则编译直接报错。

```
❌ src/renderer/src/types/knowledge-base.ts  ← 不存在，编译失败
✅ src/renderer/src/types/knowledge-base.ts  ← 必须创建
```

**规则**：如果页面写了 `import { XXX } from '../types/xxx'`，必须确保 `src/renderer/src/types/xxx.ts` 存在且导出了所有用到的类型。

### 14.2 IPC 通道名必须一致

前端 `invoke('工具名')` 的工具名必须与后端注册的**完全一致**。

```typescript
// ❌ 前端调用
await window.electronAPI.invoke('module_list')     // 下划线
// ✅ 后端注册
ipcMain.handle('module:list', ...)                  // 冒号

// ❌ 前端调用
await window.electronAPI.invoke('workflow_create_from_template')  // 不存在
// ✅ 后端实际有
workflow_create                                        // 用这个代替
```

**规则**：修改前端 invoke 调用前，先在 `ipc-handlers/` 目录和 `modules/*/module.json` 中确认工具名存在。

### 14.3 返回格式要兼容

不同 IPC handler 的返回格式可能不同：

```typescript
// 格式 A：模块工具（通过 getCapabilities 注册）
{ success: true, data: [...] }

// 格式 B：直接注册的 IPC（ipcMain.handle）
// 直接返回数据，不包装 success
[...]

// 前端必须兼容两种格式：
const res = await window.electronAPI.invoke('xxx')
if (Array.isArray(res)) setData(res)           // 格式 B
else if (res?.success) setData(res.data ?? [])  // 格式 A
```

### 14.4 模块工具 vs IPC 直接注册

| 注册方式 | 位置 | 自动 IPC | 返回格式 |
|---------|------|---------|---------|
| `getCapabilities()` → tool | `modules/*/index.ts` | ✅ 自动注册 | `{ success, data }` |
| `ipcMain.handle()` | `src/main/ipc-handlers/*.handlers.ts` | ❌ 手动注册 | 直接返回 |

### 14.5 前后端对齐检查清单

新增或修改模块功能后，逐项检查：

- [ ] 前端 `invoke('xxx')` 的工具名在后端存在
- [ ] 前端 import 的类型文件存在
- [ ] 前端处理了后端返回的数据格式
- [ ] `module.json` 的 `provides` 声明了所有工具
- [ ] `getCapabilities()` 返回了所有声明的工具
- [ ] 工具参数 schema 已定义（见第十一节）
