## 二、关键差距详解

### 🔴 1. 混合检索（Hybrid Search）— 最重要的缺失

**业内共识**：纯向量检索 < 混合检索（向量 + BM25）

**为什么需要 BM25？**
- 向量检索擅长语义匹配（"怎么提升性能" → "优化建议"）
- BM25 擅长精确匹配（搜 "error code 403" 必须精确命中 "403"）
- 混合 = 两者互补，召回率提升 15-30%

**实现方案**：
- Vectra 本身支持 BM25（`vectra` 包的 `LocalDocumentIndex` 有 hybrid search）
- 或自己实现轻量 BM25（倒排索引 + TF-IDF，~200 行代码）
- 融合策略：RRF（Reciprocal Rank Fusion）或加权线性组合

**建议**：优先级最高，直接用 Vectra 的 `LocalDocumentIndex` 替换 `LocalIndex`

---

### 🔴 2. Reranker（重排序）— 检索质量的天花板

**问题**：向量相似度 ≠ 相关性。Top-5 结果可能有 2 个不相关但向量接近的。

**方案**：
| 方案 | 复杂度 | 效果 | 推荐 |
|------|--------|------|------|
| 交叉编码器（Cross-Encoder） | 需要额外模型 | 最佳 | ✅ 推荐 |
| Cohere Rerank API | 需要 API Key | 优秀 | 适合有预算 |
| LLM Rerank | 用已有 LLM 做排序 | 不错 | ✅ 零成本方案 |

**LLM Rerank 零成本方案**：
```
给以下文档按与查询的相关性排序（1=最相关）：
查询：{query}
文档：
1. {chunk1}
2. {chunk2}
...
返回排序后的编号
```

---

### 🟡 3. 相似度阈值过滤 — 简单有效

**问题**：没有相关内容时，仍然返回低分结果，导致 RAG 回答质量差。

**实现**：`score < 0.5` 的结果直接丢弃，返回空告知用户。

**改动量**：5 行代码。

---

### 🟡 4. 语义切分（Semantic Chunking）

**业内研究**（arXiv 2505.21700）：
- 小 chunk（64-128 tokens）适合事实型问答
- 大 chunk（512-1024 tokens）适合需要上下文理解的场景
- 不同嵌入模型对 chunk 大小敏感度不同

**当前**：固定 512 字符 + 64 overlap，对大多数场景够用。

**优化方向**：
- 按嵌入向量距离判断语义边界（相邻段落向量距离大 → 在此处切分）
- 自适应 chunk 大小（短文小 chunk，长文大 chunk）

**建议**：当前策略已够用，等有性能瓶颈再优化。

---

### 🟡 5. 查询扩展（Query Expansion）

**HyDE 方案**：
1. 用户问 "怎么优化性能？"
2. LLM 先生成一个假设性回答："优化性能可以通过..."
3. 用这个回答的向量去搜索（比原始问题更匹配文档）

**多查询改写**：
1. 原始查询 → 改写为 3-5 个语义等价的查询
2. 分别搜索 → 合并去重

**建议**：HyDE 对 RAG 效果提升明显，但增加一次 LLM 调用。可作为可选功能。

## 五、结论

**当前模块基础扎实，核心链路完整。** 最大的两个差距是：

1. **混合检索**：用 Vectra 的 `LocalDocumentIndex` 替换 `LocalIndex`，获得 BM25 + 向量混合搜索
2. **Reranker**：用 LLM 做零成本重排序

这两个补上后，检索质量能达到业内一线水平。
